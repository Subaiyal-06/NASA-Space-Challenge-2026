EARTH JUKEBOX: PAKISTAN
DEVELOPMENT PLAN (for two developers using Claude Code)
=======================================================

This file answers four questions:
  1. What do WE do before any code is written?
  2. How do we use Claude Code without following it blindly?
  3. What are the build steps, in order, and what does Claude Code do in each?
  4. How is the work split between Developer 1 and Developer 2?

Companion files:
  README.md              The product plan (features, data, music, team).
  CLAUDE.md              Rules that Claude Code reads at the start of every session.
  LEARNING_GUIDE.txt     Foundations, glossary, and answers to likely judge questions.
  BUILD_LOG.txt          Decisions made so far and the "problem -> technology" table.
  logs/DEV1_LEARNING.txt, logs/DEV2_LEARNING.txt
                         Step-by-step lessons, written by Claude Code as it builds.
  logs/DEV1_BUILD.txt,   logs/DEV2_BUILD.txt
                         Step-by-step record of what was done, with which tech, and why.

(Each developer has their own two log files so Git never has merge conflicts on them.)


=======================================================
PART 1: BEFORE ANY CODE (human steps, about 1-2 hours)
=======================================================

1.1  Decide who is Developer 1 and who is Developer 2 (split in Part 4).
     Tip: the person more comfortable with Python and data takes Developer 1.

1.2  Re-read the official challenge page. Write down every required deliverable
     (for example: submission form, video, project description, data list).
     Also read the official rules about using AI tools, and plan how we will
     disclose that we used Claude Code. Being open about this is the safe choice.

1.3  Install the tools (each developer):
       - Git
       - Node.js (current LTS version) -- runs JavaScript outside a browser, gives us npm
       - Python 3 -- for the data pipeline
       - VS Code (or any editor)
       - Claude Code
     Check each one works: run "git --version", "node --version", "python --version".

1.4  Create accounts:
       - GitHub (one shared repository, both developers added)
       - NASA Earthdata (free) -- needed for MERRA-2 and GPM IMERG downloads.
         Do this FIRST. Approval can take a little time.

1.5  Create the GitHub repo "earth-jukebox". Put these files in it:
       README.md, CLAUDE.md, DEVELOPMENT_PLAN.txt, LEARNING_GUIDE.txt, BUILD_LOG.txt
     Both developers clone it.

1.6  Read LEARNING_GUIDE.txt Part 2B (Coding Foundations) and type the examples yourself.
     Then learn the 10 words that matter most BEFORE building (all in LEARNING_GUIDE.txt):
       component, state, JSON, Electron main vs renderer, anomaly, baseline,
       sonification, Tone.js Transport, scale, tension index.
     Read Part 1 and 2 of LEARNING_GUIDE.txt. It takes 30 minutes and saves hours.

1.7  Agree on three "contracts" in writing (they let two people build in parallel):
       a) The data format (README Section 7).
       b) The clock API: what the global clock exposes (year, month, mode, playing, tension).
       c) The audio API: start(), stop(), setMonth(year, month), setLayers([...]), setTension(x).
     If these three are fixed, Developer 1 and Developer 2 can work without waiting for each other.

1.8  Set the Git rules (both developers):
       - "main" branch always works. Nobody breaks it.
       - Developer 1 works on branch "dev1-engine", Developer 2 on "dev2-experience".
       - Commit after EVERY finished step, with a clear message ("S5: drone and transport").
       - Merge into main at each checkpoint (hours 12, 24, 36), not randomly.
       - If both of you must edit one file, talk first.


=======================================================
PART 2: HOW TO USE CLAUDE CODE WITHOUT FOLLOWING IT BLINDLY
=======================================================

LATEST DECISION (overrides the lesson parts of this plan):
  LEARNING HAPPENS AFTER THE HACKATHON, once the app is finished. During the build the
  default mode is BUILD ONLY: no lessons, no learning files, no exercises. Each step
  gets a 3-line plan, the build, and ONE line in the build log (logs/DEV1_BUILD.txt or
  logs/DEV2_BUILD.txt). When the app is done, say "LEARN PHASE" (or "deep dive S6") and
  the tool reads the code and the build log and writes the lessons then.
  Wherever this plan mentions lessons, teach-back or learning logs during a step, treat it
  as part of the LEARN PHASE.
  Each member also has a brief: MEMBER1_ENGINE.md (Claude Code, rules in CLAUDE.md) and
  MEMBER2_EXPERIENCE.md (Antigravity, rules in GEMINI.md).

THE LOOP (repeat for every step; steps 6-7 happen only in the LEARN PHASE):

  1. PLAN     Claude Code explains in plain English what it is about to do, which
              files it will create or change, and why. (CLAUDE.md forces this.)
  2. APPROVE  YOU read the plan. If you do not understand a part, ask:
              "Explain this like I am new to it." Only then say go.
              You approve once per step, not once per command.
  3. BUILD    Claude Code does the step without interrupting you.
  4. RUN      YOU run the app yourself and look at the result. Never trust "it works".
  5. READ     Look at what changed:  git diff   (or the VS Code source control panel).
              Skim every changed file. Ask about anything unclear.
  6. TEACH    Claude Code appends a lesson to your learning file and an entry to your
              build log (templates are in CLAUDE.md).
  7. TEACH-BACK  Close the lesson. Explain the step out loud to your teammate (or write
              3 sentences). If you cannot, ask Claude Code to re-explain.
  8. COMMIT   git add, git commit with a clear message.

SIX HABITS THAT TURN THIS INTO REAL LEARNING:
  - Ask "What would break if I deleted this file or this line?" about code you do not get.
  - Ask for "the smallest version first". Big changes are impossible to understand.
  - Change one number yourself (for example the BPM, or a color) and watch what happens.
    Every lesson has a "Try it yourself" section for this.
  - Ask "What are two other ways to do this, and why did we not choose them?"
  - If a step changes more than about 200 lines, ask Claude Code to split it.
  - Keep a list "Things I do not understand yet" at the end of your learning file.
  - WRITE IT YOURSELF (optional): when you have spare usage, say "challenge me" and Claude
    Code gives you one small piece to write. Try it first, then compare. Do this at most
    once per phase, not every step.
  - After each step, rewrite the key function from memory. If you can, you understand it.
  - Every lesson must walk through the real code line by line (what it does AND why).
    If a lesson is only a story about the project, tell Claude Code: "Show me the code
    and explain it line by line."

THE TEACHING-DEPTH DIAL:
  Teaching costs time. Use it like this:
    Hours 0-24 : full lessons (this is where the foundations are built).
    Hours 24-42: SHORT lessons (5-10 lines each). Claude Code notes "deep dive later".
    After the hackathon: read all lessons again and finish the deep dives.
  Never skip the lesson completely. A short lesson is still a lesson.
  The explanation of the KEY code is kept, but kept short (see APP FIRST below).

APP FIRST, LEARNING SECOND (usage budget):
  Priority 1 is a finished, working app. Priority 2 is learning. Lessons must never use
  up your Claude limit and leave you with an unfinished app AND unfinished learning.
  Three modes. Tell Claude Code which one to use:
    LEAN (default): short plan (about 8 lines). After each step, a lesson of about
        15-20 lines about only the 1-3 key pieces of logic (not boilerplate), plus a
        5-6 line build-log entry.
    FAST ("FAST MODE"): crunch time or low usage. One paragraph lesson, one-line log entry.
    DEEP ("deep dive S6"): full lesson with line-by-line walkthrough and exercises. Ask for
        it only when you have spare usage, ideally after the hackathon.
  Rules of thumb:
    - Bug fixes and small changes get one line in the log, no lesson.
    - When time is tight, Claude Code adds one line to the LESSON QUEUE in your learning
      file. You study the queue after the app is done.
    - Reserve at least 30 percent of your usage for hours 36-48 (bug fixing, packaging, demo).
    - Start a fresh Claude Code session for each step or phase. Long sessions get more
      expensive because the whole conversation is re-read each time. CLAUDE.md reloads
      automatically, so nothing is lost.
    - Only the files you need are read: CLAUDE.md is loaded automatically; the README and
      this plan are read only for the section that matches the current step.
    - Finish app features in priority order (see README Section 8, the cutting plan).
      Do the deep learning afterwards.
  Learning is still happening: the key-logic lessons, the build log, and the teach-back
  questions give you enough to answer judges. The deep dives make it complete later.

STARTER PROMPT FOR THE FIRST CLAUDE CODE SESSION (paste this):
  "Read CLAUDE.md, README.md and DEVELOPMENT_PLAN.txt. I am Developer 1 (or 2).
   We are on Step S1. Follow the teaching rules in CLAUDE.md: explain first,
   wait for my approval, then build, then update my learning and build logs."


=======================================================
PART 3: THE BUILD STEPS
=======================================================

Each step shows: WHO, WHAT CLAUDE CODE DOES, WHAT YOU MUST UNDERSTAND,
CHECKPOINT (how you know it works), TEACH-BACK QUESTION.

FOLDER STRUCTURE (created over time):

  earth-jukebox/
    CLAUDE.md, README.md, DEVELOPMENT_PLAN.txt, LEARNING_GUIDE.txt, BUILD_LOG.txt
    logs/                   Per-developer learning and build logs
    electron/               main.js, preload.js (the desktop shell)
    src/
      main.jsx, App.jsx     Entry point and root screen
      state/clock.js        The global clock (single source of truth)
      data/loader.js        Loads and checks the JSON files
      audio/                Music engine (engine, scale, layers, instruments)
      map/                  Globe, city markers
      weather/              Sun, Rain, Haze, QuakeRipple, AmbientGlow, ghost versions
      ui/                   Timeline, Charts, TensionMeter, StoryCard, Compare, Badges
    data/cities/*.json      One file per city (made by the pipeline)
    data/stories.json
    pipeline/               Python scripts that make the JSON from NASA/USGS data
    tests/                  Scripts that check the data and the clock logic

-------------------------------------------------------
S1  PROJECT SCAFFOLD                         [Both, together]
-------------------------------------------------------
  Claude Code: creates the project with Vite + React, adds Electron, makes an
  empty desktop window that shows "Earth Jukebox", adds npm scripts to run it,
  creates the folders and the logs/ files from the templates.
  You must understand: what Node and npm are; what Vite does (fast dev server);
  what Electron's "main process" and "renderer" are; what package.json is.
  Checkpoint: "npm run dev" (or the script we choose) opens a desktop window.
  Teach-back: "Why do we need both Vite and Electron?"

-------------------------------------------------------
S2  DATA CONTRACT, SAMPLE DATA AND LOADER    [Both, together; Dev 1 leads]
-------------------------------------------------------
  Claude Code: writes a small FAKE city file (karachi.sample.json) in the agreed
  format, a loader that reads it, and a check script that fails loudly if a
  file breaks the format.
  You must understand: JSON; why fake data first (nobody waits for NASA downloads);
  what a "schema" or "contract" is; why months are arrays of 12 numbers.
  Checkpoint: the check script passes on the sample and fails if you break the file on purpose.
  Teach-back: "What is in one city file and who produces each part?"

-------------------------------------------------------
S3  THE GLOBAL CLOCK                         [Both, together; Dev 2 leads]
-------------------------------------------------------
  Claude Code: builds the clock with Zustand: year, month, mode (Month, Year,
  Story), playing, speed, tension; a timer that moves time forward (2.5 s per month);
  play, pause, step, jump, and a small test file for the logic.
  You must understand: "state"; why ONE clock drives audio, graphs, map and glow;
  timers and drift (why a naive timer slowly goes out of sync).
  Checkpoint: console logs show the month advancing every 2.5 seconds; pause works.
  Teach-back: "Why not let each part keep its own time?"

-------------------------------------------------------
S4  TIMELINE PLAYER UI                       [Dev 2]
-------------------------------------------------------
  Claude Code: play/pause, step buttons, scrubber, mode switch, speed, keyboard
  shortcuts, leap buttons (5 and 10 years). All read and write the clock only.
  You must understand: React components, props, events, "controlled" inputs.
  Checkpoint: dragging the scrubber changes the year shown; Space toggles play.
  Teach-back: "What happens, step by step, when I press Space?"

-------------------------------------------------------
S5  AUDIO FOUNDATION                         [Dev 1]
-------------------------------------------------------
  Claude Code: a Start button (browsers and Electron may block audio until a user
  action), Tone.js setup, Transport at 96 BPM, a low drone through reverb and a
  limiter, and the audio API with stub functions.
  You must understand: Web Audio basics; Tone.js Transport (a musical clock);
  BPM (96 BPM x 4 beats = 2.5 s per bar = 1 month); reverb; limiter.
  Checkpoint: press Start and hear a steady drone; stop silences it.
  Teach-back: "Why does one bar equal one month?"

-------------------------------------------------------
S6  MUSIC LAYERS AND THE TENSION INDEX       [Dev 1]
-------------------------------------------------------
  Claude Code: the scale (A minor) and a function that forces every note onto it;
  the chord loop (Am F C G, and the tense loop Am F Dm E); arpeggio, pad, strings and
  pulse layers; setTension(x) fades layers in and out smoothly per README Section 6.4.
  You must understand: scale, chord, arpeggio, "quantize to scale", interpolation
  (smooth change), why layers enter at thresholds.
  Checkpoint: a slider from 0 to 1 (temporary test control) makes the music build.
  Teach-back: "What exactly changes when tension goes from 0.3 to 0.7?"

-------------------------------------------------------
S7  DATA INSTRUMENTS                         [Dev 1]
-------------------------------------------------------
  Claude Code: rain notes and rain noise, earthquake boom, drought filter, haze
  noise, temperature brightness; setMonth(year, month) reads a city file and drives them;
  the "orchestra grows" rule (silent before a layer's start year).
  You must understand: normalizing values to 0-1; mapping data to sound; why
  anomalies (not raw values) drive the sound.
  Checkpoint: with sample data, 1981 -> 2022 sounds clearly different.
  Teach-back: "How does a rainfall number become a sound?"

-------------------------------------------------------
S8  GLOBE INTRO AND CITY MARKERS             [Dev 2]
-------------------------------------------------------
  Claude Code: MapLibre globe, slow rotation, Start button, camera fly-in to
  Pakistan, markers that pop up one by one, click selects a city and loads its file;
  an offline fallback using a local Pakistan outline.
  You must understand: map projections (globe vs flat), tiles, markers as HTML
  elements, camera animation; what the fallback is for.
  Checkpoint: Earth zooms in; Karachi marker click loads the sample city.
  Teach-back: "What happens if the internet is off during the demo?"

-------------------------------------------------------
S9  WEATHER COMPONENTS, AMBIENT GLOW, GHOST  [Dev 2]

  You must understand: CSS animations vs canvas; why values are "compared to normal";
  CSS variables; accessibility of motion.
  Checkpoint: a test page with sliders shows every effect at several intensities.
  Teach-back: "Why does the sun not just appear every summer?"

-------------------------------------------------------
S10 CHARTS, TENSION METER, "SOUND MEETS DATA" [Dev 2]

  Teach-back: "Where do the charts get the current time from?"

  You must understand: NetCDF files; what an anomaly and a baseline are; SPI; why we

=======================================================
PART 4: HOW THE WORK IS SPLIT
=======================================================

DEVELOPER 1: ENGINE TRACK (data and sound)
  Owns: pipeline/, src/audio/, src/data/, tests/, electron packaging (S16)
  Steps: S2 (lead), S5, S6, S7, S12, S11 (audio part), S13 (logic), S14 (data), S16
  Branch: dev1-engine

DEVELOPER 2: EXPERIENCE TRACK (what people see and touch)
  Owns: src/state/clock.js (after S3), src/map/, src/weather/, src/ui/, accessibility
  Steps: S3 (lead), S4, S8, S9, S10, S11 (UI part), S13 (UI), S14 (UI), S15
  Branch: dev2-experience

STARTUP SEQUENCE (replaces the old "both together" idea; avoids conflicting files):
  1. Member 1 does S1 alone: scaffold, install ALL planned dependencies at once, create all
     folders with placeholder files, .gitignore, logs/. Push to main. (about 30-60 min)
  2. Member 1 adds the S2 minimum (sample city JSON + loader). Push to main. (about 30 min)
  3. Member 2 pulls main, creates branch dev2-experience, and starts S3 (clock) and S4.
     Member 1 continues with the S2 check script, then S5 audio.
  4. Conflict rules: only Member 2 edits src/App.jsx; Member 1 tests audio on
     src/dev/AudioTest.jsx. Package changes are committed alone, merged to main at once,
     and announced. Everyone runs "git pull origin main" before each step.
  5. While waiting, Member 2 prepares non-code work: tools, screen sketches, palette, Pakistan
     outline, city list, story cards.
  Where Part 3 says "[Both, together]" for S1-S3, follow this sequence instead.
  S17 (polish and demo) is done by both at the end.

WHY THIS SPLIT WORKS: the two tracks only touch at three places (the data format,
the clock, the audio API). Those are fixed in Part 1.7, so each person can work with
fake or stub versions of the other's part.

INTEGRATION CHECKPOINTS (merge into main, then both run the app together)
  Hour 12 : sample data + clock + audio drone + globe all run together.
  Hour 24 : full demo loop works with real data for 2 cities; first installer built.
  Hour 36 : all features in; start bug fixing only.
  Hour 40 : feature freeze.

HOW TO GROW FROM TWO DEVELOPERS TO THE FULL TEAM
  The other teammates can take: story texts, slide deck, demo video, testing with
  outsiders ("does 2022 sound more tense than 1985?"), and the data research table.
  If a teammate is strong in Python, hand them S12 so Dev 1 can focus on sound.

WHAT TO DO WHEN YOU ARE STUCK
  1. Ask Claude Code to explain the error in plain words before fixing it.
  2. Ask what the error means, then what the cause is, then what the options are.
  3. If a fix touches many files, stop and ask for the smallest fix first.
  4. Write the problem and the solution into the build log. It becomes a judge answer.
