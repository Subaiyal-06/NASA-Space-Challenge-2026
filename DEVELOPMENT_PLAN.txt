=======================================================
PART 0: SCOPE (read this first)
=======================================================

The whole project has 6 team members. THE TWO DEVELOPERS BUILD ONLY THE APP CORE.

WE BUILD (the code that makes the app run):
  - Project setup, Electron desktop shell, packaging, installers, offline behavior
  - The data layer: loading, checking and reading the city JSON files
  - The global clock, Month/Year/Story modes, smart pacing, layer start-year gating
  - App logic: events (stories, badges, quakes), ghost-weather trigger, compare logic,
    app flow (intro -> city -> player -> compare), keyboard shortcuts, voice announcer logic,
    settings (reduce motion, layers, and so on)
  - The PLUG-IN SYSTEM: contracts, registry, placeholders, connectors, dev panel
  - Integration of everything the teammates deliver, and testing it together

OTHERS DELIVER (we do NOT build these):
  - MUSIC: the sound engine (one module that follows the audio contract)
  - DATA: the finished city JSON files (and stories/records)
  - UI/UX: designs and the visual components (globe, timeline look, weather animations,
    ambient glow, charts, tension meter, story card, badges, compare view, styling)

KEY DESIGN IDEA: the app must run END TO END with placeholders from day one. Teammates'
work plugs in later through fixed contracts, without changing the core code.

=======================================================
PART 2: ARCHITECTURE (the plug-in design)
=======================================================

  City JSON files  --->  DATA LAYER (src/data)  --->  snapshots per month
                                                           |
                      CLOCK (src/state)  ---- events ---->  CONNECTORS (src/app)
                     year, month, mode,                       |            |
                     pacing, tension                          v            v
                                                  AUDIO ENGINE        UI SLOT COMPONENTS
                                                  (teammate module)   (teammate components)
                                                  via registry        via registry
                                                  placeholder: NullAudio   placeholder: grey boxes

Rules of the design:
  1. TEAMMATES' PARTS ARE PURE AND KNOW NOTHING ABOUT OUR STORE. UI components only receive
     props. The audio engine only receives plain data (snapshots). This lets teammates build
     and test them on their own.
  2. CONNECTORS (our code) read the clock and the data layer and pass props to the slots.
  3. THE REGISTRY (src/integrations/index.js) is the ONLY place that decides what is plugged
     in. Plugging in a real module = one import and one line.
  4. PLACEHOLDERS exist for every slot and for audio, so the app always runs.
  5. Each slot is wrapped in an ERROR BOUNDARY: if a plugged-in module crashes, the app falls
     back to the placeholder and shows a warning in the dev panel instead of crashing.
  6. CONTRACT VALIDATORS check teammates' modules and data loudly and clearly.
  7. ADAPTERS let us fix small differences in the data format without editing the data.


=======================================================
PART 3: THE CONTRACTS
=======================================================

Written as code in src/contracts/ (JSDoc types plus validator functions). Summary here.
Changing a contract needs BOTH developers to agree, and the teammate affected must be told.

--- 3.1 DATA CONTRACT (the data team delivers) ---
  - data/index.json lists cities: [{ id, name, lat, lon, file }].
  - data/cities/<id>.json follows README Section 7 (layers with monthly arrays, normals,
    startYear and source per layer; earthquakes; tension; interest; baseline; records;
    projection). A "schemaVersion" field is optional (default 1).
  - Missing optional parts (tension, interest, baseline, records, projection) are allowed:
    src/data/derived.js computes fallbacks from the raw layers using the README formulas,
    and the data team's values always win when present.
  - Check with: npm run check-data  (clear error messages, exits with an error if broken).

--- 3.2 DATA API (Member 1 builds; the app uses it; never read JSON directly elsewhere) ---
  getCityList()                          -> [{ id, name, lat, lon }]
  loadCity(id)                           -> Promise<City>
  getRange(city, scenario?)              -> { startYear, endYear, layerStartYears }
  getSnapshot(city, year, month)         -> {
        year, month, isProjection,
        layers: {
          temperature: { available, anomaly, value },
          rainfall:    { available, percentile, value },
          drought:     { available, spi },
          air:         { available, aod },
          quakes:      [ { magnitude, depth, lat, lon } ]
        },
        tension, interest }
  getBaselineSnapshot(city, month)       -> same shape, 1981-1990 average for that month
  getSeries(city, layer, fromYear, toYear) -> array of { year, month, value }
  getMarkers(city)                       -> { stories: [...], badges: [...] }

--- 3.3 CLOCK API (Member 2 builds in src/state/clock.js) ---
  state:   year, month (0-11), mode ("month" | "year" | "story"), playing, speed (1,2,4),
           pacing ("normal" | "skipping"), tension, interest, cityA, cityB (or null),
           scenario, futureEnabled, layers (enabled list)
  actions: play, pause, toggle, stepMonth(dir), setYear, setMonth, seek(year, month),
           leap(years), setMode, setSpeed, selectCity(id, "A" | "B"), setLayers
  events:  tick, story, badge, quake, pacing, calm, cityChange   (subscribe with clock.on)
  Timing:  one month = 2.5 seconds in Month Mode; Year Mode about 2 s per year; Story Mode
           uses smart pacing (README Feature 6B).

--- 3.4 AUDIO CONTRACT (the music teammate delivers a module) ---
  Module default-exports a factory: createAudioEngine() -> engine
  engine methods:
    REQUIRED  start()            async, called from a user click
              stop()
              setMonth(payload)  payload = { year, month, mode, tension, interest,
                                             snapshotA, snapshotB|null }
              setLayers(ids)     ids from: "temperature","rainfall","drought","quakes","air"
              setMode(mode)      "month" | "year" | "story"
              setPacing(state)   "normal" | "skipping" (skipping: hold drone, soft riser)
              setMuted(bool)
    OPTIONAL  setCity(city), setCompare(cityOrNull), setTension(x) (for a test slider), dispose()
  The engine never reads our store or the JSON files. It only uses what it is given.
  Placeholder: NullAudio (logs every call and keeps a call log shown in the dev panel).

--- 3.5 UI SLOT CONTRACT (UI/UX teammates deliver pure React components) ---
  Each slot is a default-exported component receiving ONLY props. Our connectors fill them.
  GlobeIntro     { cities, onStart, onSelectCity(id), reduceMotion }
  Timeline       { year, month, startYear, endYear, mode, playing, speed, pacing,
                   markers, onToggle, onStep(dir), onSeek(year, month), onLeap(years),
                   onModeChange(mode), onSpeedChange(speed) }
  WeatherLayer   { cityId, selected, year, month, conditions, ghost, reduceMotion }
                   conditions = { heatAnomaly, rainPercentile, spi, aod, quake|null }
                   ghost = null | { heatAnomaly, rainPercentile, spi, aod }  (baseline values)
  AmbientGlow    { states: [{ type, strength }], side: "both"|"left"|"right",
                   beatPhase, reduceMotion }
  Charts         { series, year, month, layers, mode }
  TensionMeter   { tension, interest }
  LayerToggles   { layers: [{ id, label, available, reason, enabled }], onToggle(id) }
  StoryCard      { story|null, onClose }
  BadgeToast     { badge|null }
  CompareView    { cityA, cityB, summary, changeSince, startYear, onStartYearChange }
  Legend         { layers, explanation }
  Every slot also receives { reduceMotion }. Styling and animation are entirely the UI team's.
  Placeholder: a grey box that prints the slot name and its props as JSON. This also shows the
  UI team the exact props they get.

--- 3.6 INTEGRATION FILES ---
  src/integrations/audio/       Teammate's audio module goes here.
  src/integrations/ui/          Teammate's components go here (one file per slot).
  src/integrations/index.js     The registry. Example:
        export default {
          audio: null,                 // null = NullAudio placeholder
          ui: { GlobeIntro: null, Timeline: null, ... }   // null = placeholder
        };
  A teammate module may list extra libraries in a DEPENDENCIES.txt next to it. Member 1 installs
  them at integration time. The core installs only: react, vite, electron, electron-builder,
  zustand (and test tooling).

=======================================================
PART 6: HOW TO INTEGRATE WHAT TEAMMATES DELIVER
=======================================================

DATA (from the data team)
  1. Put the files in data/ (index.json and cities/*.json).
  2. Run: npm run check-data.
  3. If the shape differs slightly, add an adapter in src/data/adapters/ (do not edit their files).
  4. If something is wrong with the data itself, report it to the data team with the error text.
  5. Run the app: open the dev panel and step through a few years.

MUSIC (from the music teammate)
  1. Put the module in src/integrations/audio/ (entry file default-exports createAudioEngine).
  2. Install anything listed in its DEPENDENCIES.txt.
  3. In src/integrations/index.js set audio to the factory.
  4. Open /dev and run the contract test: every required method must run without errors.
  5. Click Start, play a few months, test skipping (setPacing), compare (second city) and mute.
  6. Report problems to the music teammate with the message from the dev panel.

UI/UX (from the UI teammates)
  1. Put each component in src/integrations/ui/ (one file per slot, default export).
  2. Install anything listed in DEPENDENCIES.txt.
  3. Register it in src/integrations/index.js, one slot at a time.
  4. Open /dev and run the contract test: the slot must render with the sample props.
  5. Check it in the real flow. If it crashes, the placeholder returns and the dev panel says why.
  6. Visual quality is the UI team's job; we only check that it fits the contract.

RULE: plug in ONE thing at a time, run the app, commit. If something breaks, remove that one
line from the registry and the app works again.
